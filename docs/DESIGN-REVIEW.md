# 流水线设计审查结论

## 结论

整体方向合理，适合从 Agent 工作流升级为独立产品。最关键的正确决策有四个：

- 状态属于流水线，不属于模型。
- 每个阶段通过职责单一的 Artifact 连接，不使用巨型 JSON。
- 人工批准产生明确的批准结果，AI 原始提案与设计师决策可区分。
- Style Contract 必须与批准视觉参考共同使用，单靠文字无法充分约束游戏 UI 风格。

## 第一版落地时补强的部分

### 1. Artifact 需要来源、版本和失效传播

只有 `status` 不够。每个 Artifact 还必须记录上游 `source`；上游重新生成时，下游结果标记为 `stale`，否则旧布局、旧风格或旧图片仍可能被误认为有效。

### 2. 人工门禁需要成为程序规则

不是只在文案里提示“请先批准”。后端会验证：

- Screen Contract 未批准时不能生成布局。
- Approved Layout 不存在时不能生成 Style Contract。
- Style Contract 未批准与锁定时不能开始视觉探索。
- 已有项目没有批准参考页时不能执行风格重建。

### 3. 模型输出要经过解析、校验与一次修复

模型返回不是产品数据。当前实现会：

1. 去除推理标签和 Markdown fence。
2. 提取 JSON。
3. 校验公共字段与阶段必需字段。
4. 失败时携带校验错误自动修复一次。
5. 第二次仍失败则停止，不保存伪合法 Artifact。

### 4. 新旧项目分支只存在于 Style Resolution

Wireframe 理解、布局设计和视觉探索共用同一流水线；新旧项目仅在 Style Resolution 阶段分叉，完成 Style Contract 后重新汇合。这比维护两条端到端流水线更稳定。

### 5. 与 Game UI Forge 是串联关系，不是重复关系

Game UI Forge 当前的 `ui-asset-pipeline` 从视觉成稿开始，关注元素检测、提取、切图和打包；本工具在它之前完成需求理解、布局、风格和视觉方向。两者应共享基础设施并串成一条流水线，而不是互相复制功能。

## 尚需继续验证的产品风险

- 不同多模态模型对复杂 UE 的功能召回率。
- Layout Proposal 是否能稳定产生真正有差异的策略，而不是换一种措辞。
- 多页面连续生成时的 Style Drift 指标和设计师主观评分。
- 图片模型对文字、精确控件数量和布局区域的遵守程度。
- 异步生图任务在应用重启后的恢复能力；第一版会保存完成结果，但还未实现跨进程任务恢复队列。
- 已完成真实 Kunpo 多模态与 Image-GPT2 异步生图验收；后续仍需用三组真实业务样本评估设计质量。

## 建议验收样本

至少准备三组真实 UI 任务：

1. 功能密集型：商城、背包或角色养成。
2. 视觉主导型：主界面、活动页或抽卡页。
3. 已有项目延展：提供 3–5 张批准页面和一个新 UE。

每组由 UI 设计师记录：功能遗漏、布局价值、风格一致性、可参考程度和需要人工修正的时间。第一阶段成功标准应以这些指标为准，而不是只看“是否成功调用 API”。
