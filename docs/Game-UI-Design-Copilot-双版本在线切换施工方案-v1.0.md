## 1. 决策结论

采用“单入口、双运行通道、双数据空间”的架构：

```text
浏览器：http://10.8.0.176:9030
                 │
                 ▼
       版本路由层（公开监听 9030）
        │                         │
        │ classic                │ current
        ▼                         ▼
经典版应用                    新版应用
127.0.0.1:9031               127.0.0.1:9032
release=f9dc444               release=<new-release>
data=<现有根>                 data=<现有根>/version-data/v2
```

两版只共享公开入口与版本路由，不共享身份库、会话、租户项目、上传或模型设置。经典版既有数据保持原位；新版从空数据根开始。版本切换不触发复制、迁移、双写或回滚用户数据。

## 3. 目标与非目标

### 3.1 必须实现

1. 经典版 release 字节不修改、目录不覆盖、Git commit 不替换。
2. 经典版继续读取当前数据根，新版只读取独立 v2 数据根。
3. 用户可在任何版本页面看到统一版本切换控件。
4. 切换后刷新、API、上传、下载和飞书回调全部进入所选版本。
5. 两套登录会话可以同时保留，切换版本不要求每次重新登录。
6. 版本路由不可用时有明确错误；不得静默切换版本或向用户展示另一通道的数据。
7. 新版故障时可切回经典版，不执行用户数据回滚。
8. 路由层故障时可以恢复原 systemd unit，让经典版重新直接监听 9030。

### 3.2 明确不做

- 不复制经典版项目到新版。
- 不执行 Schema 1.0 → 2.0 的线上迁移。
- 不做两版数据双写、同步、合并或冲突解决。
- 不允许经典版读取新版目录，也不允许新版扫描经典版租户目录。
- 不改变飞书应用凭据、公开地址或回调地址。
- 不在仓库、release、日志或文档中保存 Secret、Cookie、token 或用户文件正文。
- 不为本项目引入数据库、容器、Nginx 或新的共享基础设施。

## 4. 固定架构契约

### 4.1 监听与服务

| 组件 | 候选 unit | 服务账号 | 监听 | 对外可见 | 责任 |
| --- | --- | --- | --- | --- | --- |
| 版本路由 | `game-ui-design-copilot-online.service` | 独立 router 账号 | `0.0.0.0:9030` | 是 | 版本选择、代理、公共切换控件、健康摘要 |
| 经典版 | `game-ui-design-copilot-v1.service` | 现有 `game-ui-design-copilot` | `127.0.0.1:9031` | 否 | 运行精确旧 release 与旧数据 |
| 新版 | `game-ui-design-copilot-v2.service` | 独立 v2 账号 | `127.0.0.1:9032` | 否 | 运行新版 release 与独立 v2 数据 |

候选内部端口必须在生产施工前由服务器登记簿和实时审计共同确认。路由 unit 保留现有正式 unit 名，以保持项目登记身份和 9030 所有权稳定；新增 lane unit 仅属于同一项目。

### 4.2 release 指针

```text
/opt/game-ui-design-copilot-online/
├── releases/20260812-113232-f9dc444/   # 永久保留，不修改
├── releases/<new-release>/             # 新版候选
├── v1-current -> releases/20260812-113232-f9dc444
├── v2-current -> releases/<new-release>
└── router-current -> releases/<router-release>
```

三个指针独立切换。不得让 v1 unit 通过通用 `current` 间接加载新版，也不得让 v2 unit 回退后误读经典版 release。

### 4.3 数据与配置

| 通道 | 数据根 | 身份/会话 | 项目数据 |
| --- | --- | --- | --- |
| classic | `/var/lib/game-ui-design-copilot-online` | 保留现有 | 保留现有 Schema 1.0 项目 |
| current | `/var/lib/game-ui-design-copilot-online/version-data/v2` | 新建独立索引 | 新建空工作区 |

环境文件建议拆分为：

```text
/etc/game-ui-design-copilot-online/router.env
/etc/game-ui-design-copilot-online/v1.env
/etc/game-ui-design-copilot-online/v2.env
```

环境文件只登记变量名称，生产值由服务器安全注入；文件保持 `root:root`、`0600`。v1 继续使用旧 Cookie 名，v2 使用独立 Cookie 名。两个应用可使用同一个飞书 App，但每个通道维护自己的身份映射、session 文件和模型设置。

文件权限同时构成隔离边界：经典版数据继续由现有服务账号持有；v2 根由独立 v2 账号以 `0700` 持有；router 账号不拥有任何 tenant 数据。三个进程不得加入可读写对方数据的共享组。release 目录可只读共享，配置值由 systemd 从 root-only 环境文件注入。

### 4.4 版本选择规则

路由优先级固定为：

1. 已验证取值的显式版本 Cookie；
2. 无版本 Cookie 但存在经典版 session Cookie 时进入 classic，保护既有登录用户；
3. 其余请求使用路由环境中配置的默认版本。

版本 Cookie 仅允许 `classic` 或 `current`，使用 `HttpOnly`、`SameSite=Lax`、`Path=/`；非法值视为未选择。版本切换使用同源 POST，并校验 Origin。禁止通过查询参数直接选择上游，避免链接或第三方页面替用户改变版本。

初次上线时默认版本必须是 classic。只有新版生产验收完成且负责人明确批准后，才允许把无历史会话的新用户默认值改为 current。

### 4.5 飞书 OAuth 路由

- classic 保持 `design_copilot_session` 和 `design_copilot_oauth`。
- current 增加可配置 Cookie 名，生产使用独立 v2 名称；默认值保持旧行为，确保桌面端和普通单版本 Web 不受影响。
- 路由收到 `/auth/feishu/start` 时记录一个短时、HttpOnly 的 OAuth 目标通道 Cookie。
- `/auth/feishu/callback` 必须优先按 OAuth 目标通道转发，完成后清除该目标 Cookie。
- 如果目标 Cookie 被篡改、缺失或与上游 state 不一致，上游按既有 state 校验失败关闭；不得尝试另一个版本。
- 用户切换版本、取消登录或回调超时都不能把授权码发送给两个上游。

### 4.6 公共版本切换控件

版本路由只对成功的 HTML 文档响应注入一个同源脚本引用；JSON、图片、字体、下载、上传和流式响应完全透传。脚本由 9030 路由层提供，因此经典版 release 无需修改。

控件要求：

- 显示“当前：经典版”或“当前：新版”。
- 明示“两版工作区相互独立，项目不会自动同步”。
- 支持键盘、清晰焦点、中文可读标签和移动窗口尺寸。
- 切换前不上传、不复制、不迁移数据；确认后 POST 选择并整页刷新。
- 所选上游不可用时展示路由层错误页和“切换到另一版本”，不得自动降级。
- 注入失败时应用本身仍可使用；固定入口 `/__versions` 必须仍能打开版本选择页。

## 5. 故障边界与回滚

| 故障 | 用户表现 | 允许的恢复 | 禁止动作 |
| --- | --- | --- | --- |
| 新版进程失败 | current 返回明确不可用页 | 切换 classic；修复或回退 v2 指针 | 不把 current 请求静默发给 classic |
| 经典版进程失败 | classic 返回明确不可用页 | 重启 v1；必要时恢复原 unit | 不让新版读取经典版数据 |
| 路由层失败 | 9030 不可达 | 恢复原 unit/env，使旧 release 直接监听 9030 | 不改用户数据、不删除失败 release |
| 新版数据异常 | 只影响 v2 工作区 | 停止 v2、保留证据、从 v2 专属备份恢复 | 不覆盖 classic 根 |
| OAuth 目标不一致 | 登录失败并要求重试 | 清除短时目标 Cookie 后重试 | 不跨通道复用 code/state |
| HTML 注入失败 | 无浮动按钮 | 使用 `/__versions` 固定页；修复注入 | 不阻断应用 HTML 返回 |

因为两版数据完全独立，应用版本回退只切 release 指针和进程，不需要逆向迁移用户数据。

## 8. 生产施工顺序

以下步骤只有在 PR-01 至 PR-06 合并、CI 通过且负责人明确授权生产施工后执行：

1. 重新只读审计服务器、登记簿、9030–9032、systemd、数据目录和当前 release。
2. 正式登记 9031/9032 作为本项目回环内部端口，并记录两个 lane unit。
3. 创建经典版数据的独立可恢复备份；验证文件数量、大小和 JSON 可解析性，不输出用户正文。
4. 上传新的不可变 release，不修改 `current` 或现有 unit。
5. 创建 v2 专属空数据根及最小权限；不复制 classic 的 `identity`、`sessions`、`tenants` 或 `settings`。
6. 使用候选环境在 127.0.0.1:9032 启动 v2，验证健康、飞书登录、创建项目、AI 调用、上传下载和重启持久化。
7. 使用精确 `20260812-113232-f9dc444` 在 127.0.0.1:9031 启动 v1，验证现有两个身份映射和既有项目仍可见；不打开项目触发任何新版迁移代码。
8. 启动尚未公开监听的路由候选，验证版本选择、HTML 注入、OAuth 固定和上游故障页。
9. 保存原 unit、环境文件元信息和恢复命令；确认经典版可在单次回滚中重新直接监听 9030。
10. 在短维护窗口内停止旧的 9030 进程，启用 v1/v2 lane 和 9030 路由。
11. 依次验证回环健康、9030 正式入口、classic 登录与项目、current 登录与空工作区、双向切换、登出和错误场景。
12. 初始默认保持 classic；至少完成约定观察期和负责人验收后，另行批准默认 current。
13. 由服务器审计流程复核 service、端口、release 指针、数据根、权限和正式入口，再更新登记簿。

## 9. 验收矩阵

| 场景 | classic 预期 | current 预期 |
| --- | --- | --- |
| 首次访问、无 Cookie | 初始上线默认进入 | 负责人批准改默认后，新访客进入 |
| 既有 classic session、无版本 Cookie | 自动进入 classic | 不抢占 |
| 显式切换 | 进入 classic，旧项目可见 | 进入 current，工作区为空或只有新版项目 |
| 同名项目 | 只存在 classic 根 | 可独立创建，不覆盖 classic |
| 登出 | 只销毁 classic session | 只销毁 current session |
| OAuth 回调 | 只消费 classic state/code | 只消费 current state/code |
| 上游宕机 | 显示 classic 不可用 | 显示 current 不可用 |
| 版本切回 | classic 数据保持原样 | current 数据保持原样 |
| 服务重启 | classic 数据仍在 | current 数据仍在 |
| 路径构造攻击 | 不能越出 classic tenant | 不能越出 current tenant |

双账号验收必须验证：两个飞书账号在两个版本中分别隔离；同名项目、同名文件、手工路径、旧下载 URL、登出和换浏览器均不能串租户或串版本。

## 10. PR 与生产权限边界

- 每个 PR 使用独立 `codex/` 前缀分支，只提交该 PR 明确范围内的文件。
- 当前工作区已有的其他未跟踪文档和图片不纳入这些 PR，不删除、不暂存、不发布。
- 创建远端分支、push、创建 PR、合并、打 tag 和发布 release 分别按 GitHub 安全工作流执行；不得将“制定方案”视为全部远端写入授权。
- 合并必须针对已核实的远端默认分支，Required Checks 全绿；禁止 force-push、绕过 Ruleset、重写历史或删除旧 tag。
- 生产写入、服务重启、9030 接管、默认版本改为 current 均是独立审批点。
- 任何阶段发现数据根交叉、Cookie 串用、OAuth code 被两个上游接收或旧 release 发生变化，立即停止，不进入下一里程碑。

## 11. 最终完成定义

只有同时满足以下条件，Goal 才能标记 complete：

1. 六个 PR 均按范围完成并通过 Required Checks。
2. 经典版 release 和经典版数据根保持不变且可访问。
3. 新版使用独立身份、会话、租户和项目根。
4. 9030 版本切换在真实浏览器中双向可用。
5. 飞书 OAuth、登出、双账号、上传下载、AI 调用和重启持久化验收完成。
6. 任一单通道故障不会自动展示另一通道的数据。
7. 路由级恢复经典版直连 9030 的步骤已验证。
8. 服务器登记簿记录最终 release、服务、端口、数据根和回滚基线。
9. 最终报告列出实际 commit、release ID、入口、验收证据和仍保留的旧 release。
