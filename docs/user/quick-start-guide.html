GAME UI DESIGN COPILOT · USER MANUAL

使用说明书 当前开发版（PR #25 及以后）

面向游戏 UI 设计师的 AI 设计流水线：从一张 UE 线框稿，走到一张可交付、全程可追溯的 UI 成图。

这是什么工具？

你把一张 UE 线框稿 + 一段设计意图交给它，AI 会沿着一条流水线逐步产出：功能契约 → 布局 → 风格规范 → 组件绑定 → 底层图 → 最终成图。每一步的产出（产物，Artifact）都由你人工检查并批准，AI 不会替你拍板；每次生成与批准都留有版本和证据，可以随时回看。

它擅长

  • 读懂 UE 线框稿，整理出页面功能契约
  • 给出可比较的布局提案与可复现的风格规范
  • 延续已有游戏的 UI 风格（严格继承模式）
  • 用你提供的真实组件切图与字体合成最终 PNG

它不做

  • 不替你批准任何产物——批准权永远在人
  • 不允许手改生成的 JSON/PNG——产物是只读证据
  • 不跳过流程——按钮置灰就是前置没完成，这是设计

适用版本与平台

本文档描述当前开发分支的界面与文案（自 PR #25 的深色界面与自绘下拉框起）。如果你使用的是更早的发布版本，个别按钮名称可能不同，以应用内实际界面为准；正式发布时本文档会标注对应版本号。

  • macOS 桌面端：主要形态，本文档所有截图级描述以它为准。
  • Windows / Linux：功能一致，通过终端命令启动（见下）。
  • Web 在线版：由组织服务端部署，浏览器访问；核心流程一致，但没有「在系统文件管理器中显示项目」等桌面专属入口，且需飞书登录。

首次安装与启动

macOS 首次运行（共四步，只有第一次需要前两步）：

  1. 安装 Node.js 22 LTS（终端运行 node -v 能看到版本号）。
  2. 安装 pnpm（版本 11，终端运行 pnpm -v 能看到版本号）。
  3. 在项目根目录运行 pnpm install 安装依赖。
  4. 之后每次启动：双击项目根目录的 Start Game UI Design Copilot.command，或运行 pnpm quick-start。

Windows / Linux：在项目根目录运行 pnpm install，然后 pnpm quick-start。

注意：.command 启动脚本不会自动安装依赖。依赖缺失时它会直接提示「项目依赖不完整，请先在项目目录运行 pnpm install」，照做即可。

启动前自检：运行 pnpm quick-start:check，一次性检查依赖是否完整、5174 端口是否被其他应用占用。

开发模式（改代码时使用）：pnpm install 后运行 pnpm dev。

配置 AI 连接（只需做一次）

工具通过 Kunpo 调用模型，两种接入方式二选一：

方式 A · 本地 Gateway（推荐）：先确认本地 Gateway 服务已在运行——127.0.0.1:9020 是它在你电脑上的默认地址，本工具不会替你启动它；然后在项目根目录 .env 里写：

KUNPO_GATEWAY_BASE_URL=http://127.0.0.1:9020/v1

方式 B · 桌面端直连：没有本地 Gateway 时，直接指向 Kunpo 服务地址与 Key：

KUNPO_API_BASE_URL=https://your-kunpo-host/v1
KUNPO_API_KEY=your-local-key

配置好后看窗口顶栏右侧：出现 Gateway 已就绪（或 Kunpo API 已就绪）说明连接成功；显示 Kunpo 未配置 则检查 .env 拼写后重启工具。连接失败、超时、模型不存在等问题的排查步骤见 docs/dev/PROVIDER-TROUBLESHOOTING.md。

模型名称可在顶栏 ⚙ 设置（模型与工作区配置）里修改：视觉理解模型、图像模型两项自由填写，保存后新任务立即生效。

真实 API Key 只保存在本地 .env 或受控服务端（Gateway），永远不要提交到代码仓库。

10 分钟练习：新项目最短路径

目标：不求质量，只求把流程完整走一遍。练习素材用仓库自带的示例线框稿 docs/user/examples/quick-start-wireframe.png（侠客阵容编成页面，来源与授权说明见 docs/user/examples/README.md）。

  1. 建立项目 — 首次打开会自动弹出创建窗口（也可以点顶栏 ＋ 新项目）。项目名称建议填「快速上手示例」，项目类型选「新项目」，点「创建并进入工作台」。项目文件默认保存在 ~/Game UI Design Projects。
  2. 00 输入 — 在右侧「UE WIREFRAME」卡片点 选择图片 导入上面的练习线框稿；在设计意图里粘贴「设计一个角色编队页面，玩家可以查看成员、调整上阵顺序并确认阵容。」（也可以留空，点 AI 解读并预填写 让 AI 先读图生成草稿），检查后点 确认意图并开始功能解读。
  3. 01 功能解读 — 等 AI 生成功能契约，浏览四类信息（必需控件 / 必要信息 / 交互状态 / 边界情况），然后点 批准功能契约。
  4. 沿界面按钮往下走 — 每个阶段底部都有下一步按钮（如「生成布局提案」「进入风格锁定」）。按钮置灰不是故障，旁边的灰字会说明缺什么。
  5. 随时看证据 — 点顶栏检查器图标，可以看到每个产物的版本、来源和 JSON。
  6. 导出成图 — 走到「04 视觉探索」生成 3 个方向，批准其中一个后即可在卡片上导出 PNG。练习到此完成；已有项目的严格继承链路见「2 路线选择」。
核心原则：只按界面提供的按钮从上到下操作。不要手动改项目目录里的 JSON/PNG 文件（生成产物是只读证据，手改会被拒绝）；任何不确定的状态，从上游重新生成永远比手工修补安全。

先选路线：这个项目是「从零探索」还是「延续已有风格」？

创建项目时的选择决定整条流水线的走法。创建时选错也没关系：已有项目可以随时在「00 输入」里切换继承强度（见下文），新项目则建议直接重建。

你的情况创建时选择走哪条路线
全新玩法/新界面，视觉风格可以自由探索新项目路线 A · 探索路线：先布局，再锁风格，最后生成 3 个视觉方向供评审
游戏已有成型 UI，新界面必须「看起来像同一个游戏」，且要交付可用的最终成图已有项目 → 严格继承（推荐）路线 B · 严格继承路线：先参考图锁风格，导入真实字体/组件并绑定，再出布局、底层图、合成、保真校验、批准与导出
有既有风格参考，只想快速生成结构底层图，不要求完整可交付页面已有项目 → 引导继承（实验性）见下方「引导继承的当前限制」——当前版本不能完成正式交付，正式生产请用严格继承

路线 A · 新项目探索路线

流程总览

00 输入需求+线框→ 01 功能契约批准→ 02 布局三选一→ 03 风格生成并锁定→ 04 生成 3 个视觉方向→ 评审批准 · 导出 PNG
  1. 00 输入：导入 UE 线框稿 → AI 预填设计意图 → 检查/补充后「确认意图并开始功能解读」。美术大方向选填（如「克制东方奇幻」），会影响后续风格与视觉生成。
  2. 01 功能解读：检查功能契约（四类关键信息），点「批准功能契约」→「生成布局提案」。
  3. 02 布局设计：AI 给出 3 套布局提案，比较区域比例、焦点路径与信息承载，选一套批准。不满意可「重新生成」。
  4. 03 风格锁定：点底部「进入风格锁定」，AI 依据布局与美术方向生成风格契约（语义色彩、字体规则、材质、几何、光影、构图）。可以导入参考图辅助，也可以不导入。核对可执行数值后点「批准并锁定」。
  5. 04 视觉探索：点「生成 3 个方向」，AI 逐张产出 保守继承 / 表现强化 / 局部创新 三个方向。可全屏检查、多选组合、写评审批注、单张重试。
  6. 交付：选 1 个方向点「批准所选方向」（选 2 个以上可「组合所选」）；点卡片上的导出按钮即可导出单张 PNG。

路线 B · 已有项目严格继承路线

流程总览

00 输入→ 01 功能契约→ 03 参考图+风格锁定→ 字体+组件+绑定→ 02 组件感知布局→ 底层图生成+污染审查→ 合成+保真+批准+导出

严格路线的推荐执行顺序是 00 → 01 → 03 → 02 → 04（先锁风格资产，再出布局）。不必记顺序——每一步完成后界面会给出下一步按钮。

开工前备好素材：

  • ≥1 张既有 UI 截图（PNG/JPG，越接近目标屏幕越好）
  • 既有 UI 使用的 OTF/TTF 字体文件
  • 组件切图：按钮/导航/页签等控件的各状态透明 PNG（按钮、导航、页签必须具备 Default、Disabled，以及 Pressed 或 Selected 状态）
  1. 创建项目：选「已有项目」，继承强度保持「严格继承（推荐）」。创建后项目进入 strict 门禁体系。
  2. 00 输入：与路线 A 相同——导入线框稿、确认设计意图。
  3. 01 功能解读：校对并「批准功能契约」。注意：严格模式下所有「必需控件」后续都要绑定组件，清单要覆盖需求中的全部元素。
  4. 03 风格锁定 · 参考图：导入既有 UI 截图，为每张设置角色与信息、逐张批准，然后「批准参考图清单」，最后「解析视觉风格」。完整操作见「4 资产与绑定 · 参考图清单」。
  5. 批准并锁定风格：核对生成的风格契约（必须是 hex 颜色、具体字号等可执行值），点「批准并锁定」，下方出现「STRICT CONTINUATION · 严格继承资产与绑定」面板，顶部四个门禁：风格规范 / 字体清单 / 组件契约 / 控件绑定。
  6. 字体清单：导入字体文件并为每个语义角色完成「确认」，最后「批准」。字段与规则见「4 资产与绑定 · 字体」。
  7. 组件契约：逐状态导入真实切图，填齐复用策略、缩放与锁定属性，最后「批准」。字段与模板见「4 资产与绑定 · 组件」。
  8. 控件绑定：为每个必需控件显式选择 组件 → 状态 → 字体角色。语义不兼容的选项会灰显并标注原因；没有任何隐式默认，必须全部显式选完才能「保存绑定」→「批准」。
  9. 生成组件感知布局：四个门禁全部批准后按钮解锁，生成布局 → 到「02 布局设计」选择方案并批准。
  10. 底层图链路：布局批准后点「建立底层规范」（自动生成底层图契约 + 结构 Guide），再点「生成底层图」产出 3 张底层图。
  11. 04 严格生产：进入视觉探索阶段下方的「STRICT PRODUCTION」面板，按固定顺序执行：「自动污染审查」→ 必要时「修复并复审」→「合成预览」→「加载字体并生成最终 PNG」→「保真校验」→「最终批准」→「导出最终 PNG」。导出必须先完成最终批准，未批准时导出按钮不可用，直接调用也会被后端阻断。每步细节见「3 阶段详解 · 04」。

引导继承（实验性）的当前限制

引导继承当前仍采用底层图（underlay-only）生成方式，同样禁止共享按钮、共享页签、导航、图标和正式文字进入图片。它与严格继承的区别主要在于部分后端门禁更宽松，但当前同样没有最终合成入口（共享组件与正式文字不参与合成），因此不能作为正式交付路线。请注意当前版本的真实边界：

  • 当前只生成结构底层图（背景与页面专属装饰）；
  • 字体、组件、控件绑定与最终合成面板仅在严格继承/锁定继承下开放，引导继承没有共享组件与正式文字的最终合成入口；
  • 因此引导继承不保证形成完整可交付页面，适合早期看结构、探方向；正式生产请使用严格继承。

两种强度可以在「00 输入」阶段的「继承强度」下拉里随时切换；切换会按依赖图让模式相关的下游批准失效，需要重新批准。已锁定的项目（锁定继承）不可再切换。引导继承的完整产品化是独立的后续任务。

五个阶段逐一拆解

左侧「DESIGN FLOW」的 5 个节点就是这 5 个阶段。节点上的彩色状态点表示进度；阶段内所有操作都在主工作区完成，阶段底部始终有「下一步」按钮。术语首次出现时括注英文，后续只用中文。

00 · 项目输入线框稿、设计意图、继承强度 01 · 功能解读功能页面契约四类信息 02 · 布局设计布局提案比较与批准 03 · 风格锁定风格契约与严格继承四门禁 04 · 视觉探索视觉方向 / 底层图、合成、保真、导出
00 · INPUT

项目输入

目标：让 AI 读懂 UE 线框稿，并由你确认设计意图。

操作步骤

  1. 导入线框稿：右侧「UE WIREFRAME」卡片点 选择图片（导入后可点「放大对照」全屏查看，之后可用「替换」换图）。没导入线框稿时，后面所有按钮都是置灰的。
  2. 设计意图：可以留空。点 AI 解读并预填写，AI 只推断画面中可见的页面目标与流程，生成一份可编辑草稿；隐藏玩法规则由你补充。检查后点 确认意图并开始功能解读（确认后仍可修改再「重新生成功能契约」）。
  3. 美术大方向（选填）：一句话风格基调，用于后续风格锁定与视觉探索，不影响功能识别。
  4. 继承强度（仅已有项目）：严格继承（推荐）/ 引导继承（实验性）。切换会让模式相关的下游批准失效；锁定继承的项目不可切换。引导继承的限制见「2 路线选择」。

页面栏（多页面管理）

顶栏下方的页面栏管理本项目的多个页面（Screen）：下拉切换当前页面、重命名、＋ 新建独立页面、复制当前页面（含全部产物）、归档其他页面。每个页面独立拥有一套线框稿、需求、功能契约、布局与绑定；而风格规范、字体、组件、参考图是项目级共享的。

01 · UNDERSTAND

功能解读

目标：校对 AI 生成的功能页面契约（Screen Contract）并批准。

界面结构

  • 契约总览：页面名称、页面目的、核心动作；「UE 来源覆盖校验」会确认线框稿里的功能没有遗漏。
  • 四类关键信息卡片：必需控件 / 必要信息 / 交互状态 / 边界情况，每张卡显示检查进度（x/y 已检查）。点卡片进入「专注检查」工作台。

专注检查里能做什么

  • 对每一条标记：已确认 / 有疑问；也可以直接编辑或删除条目、新增条目；支持搜索与按状态筛选。
  • 编辑「必需控件」时必须给出稳定 ID（小写字母+连字符，如 confirm-purchase）和语义角色（从受控词表中选择，不能是泛化的 action）。角色决定后面能绑定哪类组件。
  • 所有修改先停留在本轮草稿里，点 保存本轮修改 统一生成一个新版本；关闭时如有未保存修改会弹出确认。

底部按钮

重新解读（输入变了会提示「输入已变化，重新解读」）· 批准功能契约 · 批准后变为 生成布局提案。

02 · STRUCTURE

布局设计

目标：从布局提案中比较、调整并批准一套 Approved Layout。

操作要点

  • AI 基于功能契约生成布局提案（新项目 3 套；严格路线生成「组件感知布局」）。在目标分辨率里检查区域比例、焦点路径、安全区与实际信息承载。
  • 选择方案并批准；不满意点「重新生成」。
  • 上游（画布/需求/契约）变化后布局会标记「需更新」，旧布局只能用于对照——按提示先更新功能契约。
  • 批准后的下一步按钮随路线变化：新项目显示「进入风格锁定」；严格路线且风格已批准时显示「建立底层规范」（自动生成底层图契约 + 结构 Guide），随后是「生成底层图」。
03 · STYLE LOCK

风格锁定

目标：把美术方向沉淀成可复现的视觉规范（风格契约，Style Contract）；严格路线还要在这里完成字体、组件与绑定三道门禁。

① 参考图（已有项目必需）

导入既有 UI 截图并逐张声明用途、逐张批准，最后「批准参考图清单」——完整字段与容量规则见「4 资产与绑定 · 参考图清单」。已有项目必须批准参考图清单且至少 1 张图已批准，才能解析风格。

② 解析并锁定风格

  • 点 解析视觉风格（前置条件不满足时按钮旁的灰字会说明缺什么：严格路线需功能契约已批准；新项目需布局已批准）。
  • 如果参考图总量超出生成服务的附件容量上限，底部按钮会变成 确认省略项并继续——先在参考图区域的 Pack 面板核对哪些图被省略，确认后再点。
  • 生成的规范展示：视觉识别、语义色彩系统（可复制的色块与 hex）、材质/几何/光影/组件/构图规则。点「编辑规范」可以直接改 JSON，保存生成新版本。
  • 核对无误后点 批准并锁定。

③ STRICT CONTINUATION 面板（仅严格路线，风格批准后出现）

顶部四个门禁：风格规范 / 字体清单 / 组件契约 / 控件绑定。字体、组件、绑定的逐步操作见「4 资产与绑定」。四个门禁全绿后，点 生成组件感知布局，转入 02 布局设计批准。

04 · EXPLORE

视觉探索

目标：产出并评审视觉结果，完成交付。这个阶段的内容随路线不同：

路线 A · 视觉方向评审

  • 风格批准后点「生成 3 个方向」，产出 保守继承 / 表现强化 / 局部创新 三张方向图（逐张写入，可随时「停止剩余任务」，已完成的不丢）。
  • 每张卡片可：全屏检查、勾选加入评审、「仅重试此方向」；下方可写评审批注（会成为下一轮生成的反馈）。
  • 选 1 个 →「批准所选方向」；选 ≥2 个 →「组合所选」；都不满意 →「全部否决并重探」（批注会带进下一轮）。
  • 批准后在卡片或全屏里导出 PNG。

路线 B · STRICT PRODUCTION 面板

底层图生成后，阶段下方出现严格生产面板，顶部四个门禁：污染审查 / 最终 PNG / 保真校验 / 最终批准。严格按顺序操作：

  1. 自动污染审查：AI 审查底层图是否混入文字状、UI 状纹理等污染，输出证据与问题清单（可展开「审查证据与问题」查看）。
  2. 审查未通过时，点 修复并复审 让 AI 自动修复（有次数上限）。达到上限仍不通过时，回上游调整（布局槽位、视觉提示词）并重新生成底层图。
  3. 合成预览：确定性合成预览，检查结构与文字位置。若预览上有「TYPOGRAPHY PREVIEW」水印，说明存在未精确确认的文字图层，回 03 完成字体确认后重新合成。
  4. 加载字体并生成最终 PNG：实际加载字体文件渲染最终图。
  5. 保真校验：对最终 PNG 做多维保真检查（Fidelity），覆盖结构一致性、解码像素、资产哈希、安全区、文字溢出、控件覆盖、字体渲染证据、依赖新鲜度等维度（检查项随版本演进，以应用内报告为准）。问题按严重度分 blocker / critical / major，任何一档存在时报告都不会是通过；当前版本没有逐条豁免入口，须按报告指出的成因回上游修复后重新运行，直至通过。
  6. 最终批准：保真校验通过后点亮。批准的是本次合成清单（Composition Manifest）。
  7. 导出最终 PNG：仅在最终批准完成后开放。导出时后端会复核保真报告与当前合成结果的版本、哈希一致性；文件被外部改动会被阻断（FINAL_EXPORT_HASH_MISMATCH），未批准直接导出会被阻断（FINAL_APPROVAL_REQUIRED）。

其他常用入口

产物检查器（顶栏右侧图标）

展开后可看到当前阶段的 AI 输入、产物摘要、来源血缘、机器可读 JSON 与历史版本（每次生成/批准/修改都留有记录）。排查「这一步到底发生了什么」时先看这里。

项目管理（顶栏「管理」）

搜索、重命名、复制为独立项目、归档/恢复项目。归档项目在切换列表里显示〔归档〕标记。

参考图、字体、组件与控件绑定

这四个工作台是严格继承路线的核心门禁，全部位于「03 风格锁定」阶段。它们共同回答一个问题：AI 可以复用哪些真实资产，以什么方式复用？

参考图清单（REFERENCE INVENTORY / PACK）

生成服务只会收到 Pack（附件包）中按序列出的参考图，所以这里管理的不只是「有哪些图」，还有「每张图用来参考什么、以什么顺序发给模型」。

操作步骤

  1. 批量添加：点右上角 批量添加 导入既有 UI 截图（可多张）。
  2. 设置每张图的角色：主参考 / 组件 / 材质 / 构图 / 辅助。角色告诉模型这张图承担什么参考职责——例如「主参考」决定整体观感，「组件」用于提取控件样式，「材质」提供质感参照。
  3. 填写每张图的信息：页面类型、包含内容（顿号或逗号分隔）、基线说明、备注。这些信息会进入给模型的附件描述，写得越具体，风格解析越准。
  4. 调整顺序：卡片右下的前移/后移按钮调整附件顺序，Pack 按此顺序把图发给模型。
  5. 逐张批准：点每张卡上的 ✓ 批准（再点一次撤销）。
  6. 批准参考图清单：底部按钮，至少 1 张已批准才可用。这是解析风格的硬前提。
  7. 容量超限时处理省略项：如果参考图总量超出生成服务的附件容量上限，Pack 面板会显示「附件容量 已用 / 上限」和橙色警示「附件容量已达上限，超出的参考图已被省略，生成前必须确认」，并列出被省略的图及原因。被省略的图不会进入本次模型调用——核对省略清单，可接受就继续（此时「解析视觉风格」按钮变为「确认省略项并继续」）；不可接受就减少参考图或调整顺序把关键图提前。

字体清单工作台

严格路线只用你提供的真实字体文件渲染文字。工作台仅接收 OTF/TTF，批准前会核验授权确认、精确角色、字形覆盖和实际加载证据。

操作步骤

  1. 填写字体信息：字体 ID（如 ui-primary）、语义角色（如 button-label）、必需字形覆盖（逗号分隔，如 zh_cn、latin）。
  2. 勾选两项确认：「我确认有权在本项目中使用」——确认你有权在本项目中使用该字体，是否允许再分发取决于字体许可证，本工具不替你判断；「该角色必须精确使用此字体」——即精确确认（exact），承诺合成时该角色一字不差地用这个字体文件渲染。
  3. 选择字体：导入 OTF/TTF 文件，工具记录文件哈希与字形覆盖。
  4. 确认：为每个语义角色执行一次「确认」，把角色与字体绑定（两个勾选都勾上才能提交）。
  5. 批准：全部角色确认完成后点「批准」锁定字体清单。

常见疑问

  • 每个角色都要单独确认，不只是标题/正文两类——按钮标签、页签标签、数字等角色同样走「确认」动作。
  • 同一字体绑定多个角色不需要重新导入：导入一次后，对每个角色各做一次「确认」即可。只有字体文件本身变化（哈希不一致）时才需要重新导入。
  • 角色变更必须通过「确认」动作，不能直接编辑清单文本。
  • 身份关键角色缺少精确确认时，最终合成会被拦下，合成预览上会出现「TYPOGRAPHY PREVIEW」水印。

组件素材工作台

逐状态导入真实透明切图，构成组件契约（Component Contract）。按钮、导航、页签三类组件必须具备 Default、Disabled，以及 Pressed 或 Selected 状态——缺状态时工作台顶部会列出缺失清单。

控件绑定

编辑边界：什么能改、在哪里改

允许（推荐方式）：通过应用内的工作台编辑——功能契约的专注检查、风格规范的「编辑规范」、绑定工作台的重新选择等。保存时会生成一个新版本，历史完整留痕。

禁止：在文件管理器、编辑器或脚本中直接修改项目目录里的管线产物与证据文件，包括但不限于：

  • 合成输出（Composition Output）与最终 PNG；
  • 污染审查（Critique）的原始响应；
  • 保真报告（Fidelity Report）；
  • 其他产物 JSON 与 workflow/ 下的状态与历史。

生成产物是只读证据，手改会被直接拒绝（GENERATED_EVIDENCE_READ_ONLY）或在导出复核时被哈希校验拦下。

历史与恢复

产物检查器与 workflow/artifact-history.json 可以回看每个产物的全部历史版本。当前版本没有一键恢复历史版本的按钮——需要回到某个旧状态时，从对应上游重新生成；重大操作前，复制整个项目目录就是一份完整快照备份。

产物（Artifact）与项目目录

流水线每一步的输出都是一个产物（如 screen-contract.json、approved-layout.json、composition-manifest.json），带有 schema_version / id / version / status / source 五项元信息，全程可追溯。项目默认保存在 ~/Game UI Design Projects，结构为：

项目目录/
├── project.json          # 项目主文件
├── screens/              # 每个页面一套：输入、契约、布局、绑定、底层图、合成…
│   └── main/
├── style/                # 项目级共享：风格契约、字体清单、组件契约、参考图、切图
└── workflow/             # 流水线状态与产物历史（只读，勿手改）

Stale（需更新）传播机制

改了上游，所有受影响的下游产物会自动标记「需更新」，防止旧批准被误用。触发条件举例：改控件的 id / role / required、换参考图重新解析风格、重新生成布局、编辑绑定……

恢复方法：从变更点开始，按依赖顺序重新生成、重新批准。例外：只改控件的显示名（label）不会触发 stale。

不要试图手工删除 stale 标记或编辑产物 JSON——生成产物只读，手改会直接报错（GENERATED_EVIDENCE_READ_ONLY），唯一解除方式是重新生成。

门禁与证据链（严格路线）

strict 模式的每个批准都依赖可复验的证据而非模型自述：图像证据（底层图/审查标记图/组件板落盘并记 sha256）、语义证据（模型审查原始响应落盘）、像素证据（保真校验实时解码输出 PNG 计算摘要）、引用一致（合成清单 ↔ 合成输出 ↔ 保真报告三层互相引用，任何一层漂移都会被拦下）。

这就是为什么严格路线按钮置灰特别多——每一个置灰都是缺某项证据，照提示补齐即可，不存在「绕过」的入口。

两条铁律

  • 生成产物只读：手改产物 JSON/PNG 会直接报错，唯一恢复方式是重新生成。
  • 重新生成 > 手工修补：任何不确定的状态，从最上游重新生成永远比手改安全；重大操作前先复制项目目录备份。

遇到问题先对号入座

流程与按钮

流程按钮置灰 / 提示「xxx is required」？
不是故障，是流程顺序问题。按钮旁的灰字会说明缺什么，回上游工作台补齐对应批准即可。
stale下游全变「需更新」了？
说明你改了上游。从最上游变更点开始按依赖顺序重新生成、重新批准。若只改了控件显示名仍 stale，检查是否同时动了 id / role / required。
流程切换继承强度后很多批准失效？
这是预期行为：严格 ↔ 引导切换会按依赖图使模式相关的下游批准失效，按提示重新批准即可。锁定继承的项目不可切换。
流程strict 下提示 UNDERLAY_SPEC_REQUIRED？
缺布局 Guide 就生成底层图会被拦截——strict 无捷径。回 02 布局阶段点「建立底层规范」（底层图契约 + Guide），再生成底层图。
流程「解析视觉风格」变成了「确认省略项并继续」？
参考图总量超出了生成服务的附件容量上限，部分图片已被省略、不会进入本次模型调用。先在参考图 Pack 面板核对省略清单：可接受就点该按钮继续；不可接受就减少参考图或把关键图顺序提前。

资产与门禁

字体字体导入后还要点什么？
导入 ≠ 确认。必须勾选「我确认有权在本项目中使用」（是否允许再分发取决于字体许可证，本工具不替你判断）与「该角色必须精确使用此字体」，然后对每个语义角色点一次「确认」。同一字体绑定多个角色不用重复导入；字体文件变化时才需重新导入。身份关键角色缺精确确认，最终合成会被拦下。
合成preview 合成图上有水印？
存在未精确确认的文字图层。去 03 字体区完成各角色的「确认」后重新合成，水印即消失。
绑定绑定批准报 BINDING_* 错误？
按违规明细修正绑定（角色词表、状态匹配、文字策略）后重新校验批准。注意：编辑绑定会自动清除旧批准，需要重新批准。不兼容选项会灰显并标注原因，优先选非灰选项。
审查底层图污染审查一直不通过？
先「修复并复审」；达到修复次数上限（UNDERLAY_REPAIR_LIMIT）后，调整上游（布局槽位、视觉提示词）重新生成底层图。
保真保真校验失败（FIDELITY_GATE_FAILED）？
报告中的问题按严重度分为 blocker / critical / major，任何一档存在报告都不会是通过。当前版本没有逐条豁免入口：按报告指出的成因回上游修复（布局、组件、字体或重新合成），再重新运行保真校验，直至通过。若报 FIDELITY_EVIDENCE_STALE，通常是批准前项目文件被外部动过，重跑保真校验即可。
导出导出按钮不可用 / 导出报错？
严格路线的导出顺序固定为：最终 PNG → 保真校验通过 → 最终批准 → 导出最终 PNG。未最终批准时导出按钮不可用，绕过界面也会被后端阻断（FINAL_APPROVAL_REQUIRED）。FINAL_EXPORT_HASH_MISMATCH 表示输出文件被外部改动，重新合成后再导出。

连接与运行

启动双击 .command 提示「项目依赖不完整」？
启动脚本不会自动安装依赖。在项目根目录运行 pnpm install 后再启动；也可用 pnpm quick-start:check 一次性检查依赖与 5174 端口占用。
连接顶栏显示「Kunpo 未配置」？
检查项目根目录 .env 的 KUNPO_GATEWAY_BASE_URL（推荐 http://127.0.0.1:9020/v1），保存后重启工具。配置查找顺序：DESIGN_COPILOT_ENV_FILE 指定的文件 → 项目 .env。
连接AI 生成超时 / 鉴权失败？
检查 .env 与设置里的模型名（模型名必须受服务端支持）。临时失败不会丢已完成的证据链，点错误条上的「重试」即可。详见 docs/dev/PROVIDER-TROUBLESHOOTING.md。
运行生图进行中想停？
视觉探索生成时可以点「停止剩余任务」；已写入的图片不会丢，之后可「补全缺失方向」。
运行想看完整错误码含义？
全部错误码见 docs/dev/ERROR-CATALOG.md（与代码注册表双向校验）；失败恢复路径见 docs/user/FAILURE-RECOVERY.md。

兜底三原则

  1. 重大操作前复制整个项目目录 = 完整快照备份；
  2. 任何不确定的状态，从最上游重新生成永远比手工修补安全；
  3. 证据都在：产物检查器 + workflow/ 历史可以回答「这一步到底发生了什么」。
